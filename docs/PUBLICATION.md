# Publication policy and recovery

M3 publishes an operator-selected local report. Automatic PR event handling is M4; author assessment and human decisions follow later.

## Evidence policy

Each candidate retains its provider, reported model, CLI version, and candidate index. The publisher derives its plan from original schema-valid candidates and checks exact source evidence overlapping a valid diff hunk line. Description, trigger, and impact must contain substantive text rather than empty/placeholder values. These mechanical checks do not prove the natural-language claim is correct.

The first implementation combines only exact description/trigger/impact/evidence strings (apart from outer whitespace) at the same repository/PR/path/side/line. Titles and severity are excluded from the fingerprint; merged groups retain all origins and the highest severity. It does not collapse near-matching prose or use votes. Distinct claims at the same anchor are held as potential conflicts or separate defects, with claim excerpts in the summary and full details in the local plan.

Unanchored/unsupported candidates and inline-budget overflow are also held. Publication plans preserve their full text and explanations. A summary includes bounded excerpts and a count of additional retained candidates; it never invents a comment coordinate. HTML/Markdown and mentions from model text are escaped, and tool identifiers are generated by the coordinator.

## Validation before writes

```text
strict report schema and integrity/provenance checks
  -> acquire per-PR local lock
  -> read current PR head/base and readiness
  -> re-fetch bounded Git source and compare the entire packet
  -> save plan/preview
  -> authenticate publisher and reconcile existing owned markers
  -> journal intent, recheck freshness, create COMMENT review
  -> reconcile/patch owned marked inline bodies
  -> recheck freshness and confirm remote IDs/bodies
```

Head or base changes require a fresh review. Metadata/coverage/source differences also invalidate the supplied packet. The publisher never remaps an old finding to new source. It refuses simulations and unsuccessful reports; partial reports require `--allow-partial`. Local hashes are consistency checks, not signatures or proof of a model invocation.

GitHub cannot make a client-side freshness check atomic with a subsequent push. Reviews explicitly reference the captured head SHA. If a push races the request, final checks fail and the journal is marked superseded; a comment at the older SHA is historical, not evidence that the newer revision was reviewed.

## Ownership and identifiers

The current CLI uses a user token resolved through `GET /user`. The same publisher account should be used across runs. GitHub App/Actions installation-token identity support is a later integration.

A submitted review has a publication marker derived from report, policy, and snapshot hashes. Inline comments have a stable claim fingerprint plus a snapshot scope. Reconciliation requires the authenticated publisher's user ID, exact marker, COMMENTED review state, and reviewed/original commit and anchor. Replies are excluded even if they quote a tool marker. Foreign/unmarked comments are never updated.

Fresh reports for the same snapshot can reuse matching owned inline findings and update their severity/provenance body. New heads use a different snapshot scope, preserving earlier discussions. A finding disappearing from a newer review never deletes/resolves the old thread or establishes that it was fixed.

## Lost responses and retries

Journal states are `prepared`, `sending`, `uncertain`, `complete`, and `superseded`. Intent is persisted atomically before a create/update request. Read requests retry transient failures at most twice; writes are not automatically retried.

After an ambiguous create error, the publisher queries the review/comment lists. If it finds its submitted review and all expected inline comments, it completes the journal. If the outcome is still unresolved, it stops. Re-running the command reconciles again; it does not send a repeat create just because no review is visible yet. This favors duplicate prevention over automatic recovery from an uncertain request that never reached GitHub.

If a known review marker exists but expected comments are missing, or duplicate/incorrect owned markers exist, publication stops for inspection. A lost PATCH response is recovered by reading the owned comment body on the next invocation. Authentication/validation failures with a definite negative response are surfaced without automatic retry.

Create uncertainty is checked across the PR's journals for the same snapshot, not only the current report ID. Changing the comment budget, policy, or report does not permit a second POST while an older create intent for that snapshot remains unresolved. Reconcile the original report with its original policy first. A different reviewed head/base is a separate historical snapshot; its findings are not silently mapped onto the earlier one.

Do not discard an uncertain journal until the remote outcome is verified. If a publisher crashes, its local lock may remain; verify no publisher is active before removing `publisher.lock`. Changing working directories requires a shared `--state-dir` to share locks/journals.

## Concurrency boundary

Local locks protect only processes sharing the same state directory. Remote markers reconcile completed writes, but do not provide a distributed compare-and-swap. Two machines can both observe no review and create one concurrently. Distributed locking is deferred.

CI callers must serialize the publishing stage per repository/PR and avoid cancelling an in-flight publisher. The M4 workflow should use a group like:

```yaml
concurrency:
  group: agent-pr-review-publish-${{ github.repository }}-${{ inputs.pr_number }}
  cancel-in-progress: false
```

This is guidance for the future CI publisher, not an installed automatic review workflow.

## Verification

Dedicated test PR [#3](https://github.com/phootako630/agent-pr-review/pull/3) received one real inline finding and one COMMENT review summary from a Claude review. A wrapper simulated response loss after the real create succeeded; remote reconciliation and repeat invocation kept the counts at one each. A subsequent push caused the old report to be rejected while the historical comment remained. Offline tests cover ambiguous outcomes without remote creation, lost updates, stale head/base, invalid anchors, ownership/replies, historical revisions, and local lock contention.
